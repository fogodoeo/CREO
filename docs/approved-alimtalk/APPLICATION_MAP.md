# 알림톡 적용표

확인일: 2026-09-11. 알리고의 **승인 상태**와 서비스의 **적용 상태**를 구분한다. UL_2138·UL_2139·UL_2144와 주관사 UL_2785를 실행 기본값과 실제 이벤트에 연결했다. UL_2129·UL_2136은 예비다.

## 3시 30분 예약 작업의 구현

- `vendor_payment_method_registered → UL_2138`, `buyer_card_link_ready → UL_2139`, `vendor_payment_reported → UL_2144`로 연결했다.
- 최초 결제방식 저장 또는 승인 후 실제 변경은 2138, 배송지 단독 변경은 0883이다. 동시 저장에는 업체당 한 건만 생성하고 변경 없는 업체에는 알리지 않는다.
- 구매자 저장 내용과 알림 큐를 같은 SQLite 트랜잭션에 기록한다. 실패 시 둘 다 되돌리며 같은 내용 재저장·동시 중복 요청·재시작으로 중복 알림을 만들지 않는다.
- Render 환경변수 키 목록과 연결 환경 그룹을 읽기 전용 확인했다. 템플릿 정의를 덮어쓰는 환경변수는 없었다. 비밀값은 열거나 변경하지 않았다.
- `/health`의 `checkoutNotifications.templates`에 실제 선택된 코드도 표시하므로 배포 후 세 코드와 준비 상태를 확인할 수 있다.
- 실제 메시지를 보내지 않는 SQLite 테스트와 로컬 구매자·업체 페이지에서 카드 URL 저장/표시를 검증했다. 아래 '코드 대조 결과'는 변경 전 기준의 감사 기록이다.

## 새 승인 5종

UL_2129~UL_2144는 연속된 16종이 아니다. 계정 목록에서 확인한 해당 범위의 템플릿은 아래 5종이며 모두 승인완료, 채널추가 버튼 포함, 알리고 관리 화면의 대체문자는 발송안함이다. 코드별 JSON에 본문·변수·버튼 원문을 보관했다.

| 코드 | 언제 | 수신자 / 연결 페이지 | 적용 판단 |
| --- | --- | --- | --- |
| UL_2138 | 구매자가 결제방식을 저장해 실제 반영됨 | 해당 업체 / `/w/#{업체접속코드}` | 결제방식 등록 전용으로 연결. `#{결제방식}`에 계좌이체 또는 카드결제 전달 |
| UL_2139 | 카드결제를 선택한 구매자에게 업체가 결제 URL 등록 | 해당 구매자 / `/d/#{접속코드}` | `buyer_card_link_ready`의 UL_0884 대체 |
| UL_2144 | 구매자가 결제 사실을 신고하고 확인 요청 | 해당 업체 / `/w/#{업체접속코드}` | `vendor_payment_reported`의 UL_0883 대체 |
| UL_2129 | 구매자가 일반 거래 진행 정보를 등록 | 해당 업체 / `/w/#{업체접속코드}` | 예비. 결제방식·결제 신고에는 각각 2138·2144 우선 |
| UL_2136 | 업체가 구매자의 일반 거래 진행 정보를 등록 | 해당 구매자 / `/d/#{접속코드}` | 예비. 카드 링크 등록에는 2139 우선 |

2129와 2136은 같은 사건에 추가로 보내는 템플릿이 아니다. 구체적인 새 등록 사건과 수신자가 필요할 때만 연결한다. 승인·반려, 운영자 변경 승인 요청, 주관사 입금 알림에 무조건 재사용하지 않는다. 특히 2136의 '업체에서 등록'은 운영자가 변경을 반려한 사실과 다르다.

## 운영 흐름의 목표

| 단계 | 행동 | 보내는 알림 | 처리 상태 |
| --- | --- | --- | --- |
| 낙찰 | 운영자가 첫 낙찰 확정 | 구매자 UL_0880 + 업체 UL_0882 | 기존 유지 |
| 추가 낙찰 | 동일 구매자 추가 낙찰 확정 | 구매자 UL_0881 + 해당 업체 UL_0882 | 기존 유지 |
| 수령·결제 선택 | 구매자가 결제방식을 최초 저장 또는 실제 변경 | 업체 UL_2138 | 연결 구현 완료 |
| 수령정보만 변경 | 구매자가 배송지 등 수령정보 저장 | 업체 UL_0883 | 기존 유지, 결제방식 알림과 중복 방지 |
| 카드 URL | 업체가 구매자가 요청한 카드결제 URL 등록 | 구매자 UL_2139 | 기존 UL_0884 대체 |
| 외부 결제 안내 | 업체가 다른 결제 앱에서 직접 알림을 보낸 뒤 외부 발송 처리 | 별도 구매자 알림 없음 | 기존 `external_notice` 제외 분기 유지 |
| 결제 신고 | 구매자가 '결제했어요'를 눌러 확인 요청 | 업체 UL_2144 | 기존 UL_0883 대체. 실제 결제 확정 아님 |
| 결제 확정 | 업체가 실제 입금·카드 승인 확인 후 완료 처리 | 구매자 UK_9278 | 기존 유지. 구매자 신고 없이도 업체가 확인 가능 |
| 배송비 입금 신고 | 업체가 '배송비 입금했어요' 확인 | 주관사 등록 수신번호에 UL_2785 | 주관사 전용 정산 링크 연결. 실제 입금 확정 아님 |

수령정보와 결제방식을 한 번에 저장했다면 목표는 업체에 2138 한 건으로 알리고 페이지에서 두 정보를 함께 보여주는 것이다. 배송지만 바뀌면 0883, 결제방식이 실제 바뀌면 2138로 나눈다. 동일 내용 재저장에는 재발송하지 않는다. 승인 대상인 변경은 요청 단계에서 '선택이 변경됐다'고 알리지 않고 실제 승인·반영 후 처리한다.

외부 결제 앱 이용자는 구매자 페이지에 돌아와 '결제했어요'를 누르지 않을 수 있다. 그 클릭이나 2144 발송을 결제 완료의 필수 단계로 만들지 않는다. 업체가 직접 결제 확인 완료하면 UK_9278로 마무리한다.

## 코드 대조 결과 / 적용할 곳

기준 커밋: `687d05d`.

- `approved-alimtalk.js`: 실행 기본 매핑. 아직 `vendor_payment_reported → UL_0883`, `buyer_card_link_ready → UL_0884`이다. 새 JSON을 추가하는 것만으로 바뀌지 않는다.
- `config/kakao-alimtalk-templates.json`: 별도 보관 설정도 구 매핑이다. 실제 전환 시 실행 기본값과 같이 맞춰야 한다.
- `checkout-notifications.js`: `ALIGO_KAKAO_TEMPLATES_JSON`의 키별 정의가 기본값보다 우선한다. 실제 운영 환경변수의 구 정의가 남아 있으면 코드 변경만으로 전환되지 않을 수 있다. 이번에는 운영 환경변수 내용을 조회·변경하지 않았다.
- `platform-api.js → enqueueVendorPaymentReport`: 2144로 교체할 실제 결제 신고 경로. 업체명·구매자명·업체접속코드 변수가 이미 있다.
- `platform-api.js → enqueueBuyerStatusNotification`: 2139로 교체할 카드 URL 등록 경로. 구매자명·업체명·접속코드 변수가 이미 있다. `vendor-checkout/card-link`의 외부 발송 제외 분기는 유지한다.
- `platform-api.js → enqueueShippingRegistered`: 현재 수령정보와 결제방식을 함께 묶어 `vendor_shipping_registered`로 알린다. 2138 적용 시 이전/현재 결제방식 비교, `결제방식` 변수, 수령정보 알림과의 단일 발송 분기가 필요하다.
- `vendor_card_requested`: 템플릿 키와 매핑은 있으나 현재 API 이벤트 생성에서 직접 사용하는 호출은 없다. 이 키에 2138만 넣고 '적용 완료'로 판단하면 안 된다. 계좌이체도 포함하므로 새 `vendor_payment_method_registered` 같은 명확한 이벤트 키가 적합하다.
- `operator_checkout_change`, `buyer_checkout_change_reviewed`: 기존 임시 매핑이 남은 별도 과제다. 새 판매업체·구매자 템플릿으로 일괄 교체하지 않는다. 실제 수신 역할과 승인/반려 본문을 맞춘 전용 템플릿이 필요하다.

실제 전환 때는 코드·승인 본문·버튼·환경변수를 함께 대조하고, 격리된 테스트에서 변수 치환, URL/외부 발송 분기, 중복 클릭, 같은 내용 재저장, 변경 승인 경계를 검증한다. 이미 보낸 알림이나 보관 중인 과거 이벤트를 일괄 재발송하지 않는다. 실제 테스트 전송은 별도 요청 범위에서만 실행한다.

## 주관사 UL_2785

- 2026-09-11 알리고 목록에서 **승인완료**, 이름 **주관사 배송비 입금 접수 알림**, 대체문자 **발송안함** 확인. 승인 원문은 `UL_2785.json`에 보관.
- 업체의 배송비 입금 신고 → 주관사 페이지에 등록한 수신번호.
- 버튼: 배송비 정산 확인 → `https://creok.onrender.com/o/#{주관사접속코드}`.
- `organizer_shipping_reported`를 alimtalk로 생성한다. 업체명, 입금금액(원 제외), 해당 채널 주관사접속코드를 전달한다. 기존 주관사 링크를 재사용하고 없거나 만료된 경우 발급한다.
- 입금 신고와 알림 큐는 함께 저장하며 중복 클릭은 재발송하지 않는다. 과거 문자 이벤트는 일괄 재발송하지 않는다.
- 실제 입금 확인 완료가 아니라 업체의 확인 요청이다. 주관사의 확인 처리 전에는 받은 금액으로 계산하지 않는다.

## 대체문자 설정 구분

이번에 확인한 5종과 2785의 알리고 관리 화면은 모두 **발송안함**이다. 반면 현재 앱의 일반 알림톡 이벤트는 코드에서 `failureSmsFallback: true`와 API `failover=Y`를 사용한다. 관리 화면 설정만 보고 '앱에서도 문자가 절대 안 간다'고 판단하면 안 된다. 전환 시 기존 사용자가 요청한 알림톡 실패 시 문자 대체 정책과 각 API 요청 값을 함께 확인한다. 이번 문서 정리에서는 어느 설정도 바꾸지 않았다.
