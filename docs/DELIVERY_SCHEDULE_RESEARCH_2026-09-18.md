# 파르게·도도시 수령 예정일 조사

조사일: 2026-09-18 (한국 시간)

## 결론

두 배송사 모두 공개된 지점별 일정으로 수령 예정일을 계산할 수 있다. 경매일은 첫 배송 회차를 찾는 기준이며, 경매일에 일수를 더하는 것으로 끝내면 안 된다. 사용자가 확인한 경매 운영 방식에서는 업체가 개체를 바로 전달하므로 일반 고객용 **맡김일은 경매 일정의 계산 조건에서 제외한다**.

`방송 종료 → 출발 지점의 가장 가까운 수거일(발송 예정일) → 이동일·노선 예외 → 도착 지점의 수령 예정일`

방송 종료 이후 이용 가능한 수거 회차를 기준으로 자동 계산한다. 주관사가 모든 정상 건을 매번 확정하는 단계를 추가하지 않는다. 운휴·일정 충돌·회차를 놓친 건만 확인하고, 실제 예약 결과나 주관사의 회차 변경이 있으면 이를 우선한다. 예정 수거일이 왔다는 이유만으로 실제 발송 완료 상태를 바꾸지는 않는다.

지점별 예외, 휴무, 제주 노선, 실제 예약 결과를 반영해야 한다. 조사 단계이며 운영 사이트에 일정 계산기나 배송일을 적용하지 않았다. 예약·결제·알림 발송도 하지 않았다.

## 확인한 공식 자료

- 파르게 배송 안내: https://parge.co.kr/guide
- 파르게 배송 신청: https://parge.co.kr/booking
- 파르게 공개 일정: https://parge.co.kr/api/delivery-schedules
- 파르게 공개 지점: https://parge.co.kr/api/partners
- 도도시 노선 선택: https://www.dodosi.co.kr/113
- 도도시 페이지가 직접 사용하는 공개 일정표 3종: `dodosiShopData`, `dodosiEditData`, `dodosiDeliveryData`
- 도도시 노선별 공개 상품 옵션과 같은 페이지의 수령일 계산 코드

파르게 일정 28개, 도도시 지점 일정 107개·이동 예외 129개·노선 행 248개를 확인했다. 도도시는 최신 노선표의 대구 출발 상품 15개를 따라가 출발 옵션과 도착 옵션 99개를 다시 읽었다. 상품 옵션 조회만 했으며 장바구니와 주문은 만들지 않았다.

## 파르게

### 대구 출발과 일반 주간 운행

등록된 출발 지점 이름은 **크레오 대구본점**이다. 이 지점의 `pickupDayLabel`은 토요일, `collectDayLabel`은 월요일이다. 같은 행의 `deliveryDayLabel: 화요일`은 해당 지점으로 들어오는 배송 일정이므로 모든 대구발 배송의 도착 요일로 사용하면 안 된다.

공식 안내의 일반 운행표:

| 요일 | 운행 |
| --- | --- |
| 월 | 수도권·경상권 수거 |
| 화 | 충청·구미·대구 배송 |
| 수 | 경상권 배송 |
| 목 | 수도권 배송 |
| 금 | 강원 배송 |
| 토 | 제주 항공·당일 도착 |
| 일 | 전라도·진주·논산 배송 |

목적지의 개별 일정이 일반 운행표보다 우선해야 한다. 예를 들어 공개 지점 일정에는 구미 레포리아 목요일, 하남 미사 라이언게코 금요일 같은 예외가 있다.

최소 픽업 1일 전 예약이 필요하며 실제 도착 안내를 받고 수령하는 방식이다. 예정일 계산이 예약 완료를 뜻하지 않는다.

### 공개 자료 간 불일치

예약 페이지의 공개 계산 코드는 선택한 **맡김일 이후** 가장 가까운 목적지 요일을 찾으며, 출발 지점의 수거일을 일반 도착일 계산에 넣지 않는다.

따라서 코드 분석상 토요일 대구 맡김 → 일요일 전라 도착이 산출될 수 있지만, 대구 수거일은 월요일로 등록되어 있다. 실제 예약 화면의 해당 조합은 로그인 요구로 검증하지 못했다. 이 결과를 실제 확정 일정이나 재현 완료된 주문 오류로 단정하지 않는다. 경매용 계산기는 이 맡김일 기준 계산을 복사하지 않고 **월요일 수거 이후의 목적지 배송 회차**를 찾는다. 수거·이동·도착 일정이 서로 충돌하면 **일정 확인 필요**로 처리한다.

제주도 주의가 필요하다. 공개 일정 API의 오래된 제주 요일과 달리 현행 배송 안내 및 예약 코드에는 **2026-09-19부터 매주 토요일 항공 출발·당일 도착** 규칙이 있다. 대구 토요일 맡김과 같은 날 제주 도착이 가능한지는 출발 회차 확인 없이 자동 확정하지 않는다.

## 도도시

### 대구 출발

등록된 출발 지점 이름은 **크레용(대구)**이다.

- 상품의 맡기는 날: 화요일·토요일
- 지점 일정의 수거 방문: 수요일·일요일
- 도착일은 목적지 상품의 `찾는날` 옵션에서 가져온다.
- 정기 휴무와 지점 휴가 날짜가 별도 데이터로 제공된다.

공식 사이트의 일반 계산 순서는 맡김일 → 다음 수거일 → 이동일 가산 → 목적지 수령 요일 선택이다. 경매용 계산에서는 맡김일 단계를 제외하고 **방송 종료 이후의 수거일부터** 같은 이동일·목적지 규칙을 적용한다. 이동일은 기본 1일이며, 대구에서 양산 크레용·브리지데이 및 부산 일부 지점 등으로 보내는 경우 3일을 가산하는 예외가 있다. 지점 휴무일이면 전날로 조정하는 코드도 있어, 조정 후 수거·필요 이동일보다 이르지 않은지 다시 검증해야 한다.

### 목적지별 상품 옵션 예시

| 도착 지점 | 찾는 요일 |
| --- | --- |
| 서울 방배 다이노마켓 | 화·토 |
| 서울 서대문 네스트렙타일 | 수·토 |
| 대전 유성 디어렙 | 월·금 |
| 원주 보스게코·춘천 토리멀파크 | 수 |
| 양산 물금 크레용 | 목·일 |
| 부산 해운대 어반네이쳐 | 목·일 |
| 제주 티그리스게코 | 목, 월 2·4번째 회차 |

같은 권역 안에서도 요일이 다르므로 지역명만으로 계산하지 않는다.

### 이번 회차에서 중요한 휴무

조사 시점에 지점 107개 중 106개의 휴가 기간이 **2026-09-24~2026-09-27**로 등록되어 있다. 대구 크레용도 포함된다. 제주 티그리스게코 행은 이 휴가 기간이 비어 있다. 제주 행이 비었다는 사실만으로 연휴의 모든 이동편이 정상 운행한다고 단정할 수는 없다.

도도시의 현재 화면 코드는 가장 이른 수령 후보가 휴가 기간이면 그 선택지를 비활성화한다. 이를 무시하고 다음 주 날짜로 자동 확정하면 공식 선택 결과와 달라질 수 있다.

예를 들어 9월 17일 방송 종료 후 대구 출발이라면 도도시의 다음 수거일은 9월 20일이다. 대전 유성 디어렙은 계산상 9월 21일, 서울 방배 다이노마켓은 9월 22일, 원주 보스게코는 9월 23일 후보가 나온다. 양산 크레용은 3일 이동 예외를 거쳐 9월 24일 후보가 나오지만 휴가 기간에 해당한다. 일반 고객용 9월 19일 맡김일은 이 경매 계산의 전제 조건이 아니다. 모두 공개 규칙을 적용한 예시이며 실제 예약 결과는 아니다.

### 지점 식별과 기존 수집기 주의점

- 도착 옵션 99개 모두 일정표에서 동일한 이름을 찾았다. 그러나 다이노마켓과 크레스타는 이름이 중복되므로 **지역·지점명 조합**으로 식별해야 한다.
- 공식 페이지의 일부 지점 탐색은 부분 문자열 비교를 사용한다. 우리 쪽에서 이 방식까지 복사하면 본점/분점이 섞일 수 있다.
- `shipping-rate-refresh.js`는 도도시 상품 번호 14개를 고정해 두었다. 현재 공식 대구 출발 노선표는 15개이며 서울B·경기B/C·충청A·전라·경상A·부산 등의 상품 번호가 다르고 제주가 추가되어 있다. 예전 상품이 즉시 무효라는 뜻은 아니지만, 일정 수집은 최신 노선표에서 출발해야 한다.
- 현행 수집기는 도도시 `day`를 읽지만 구매자 배송 선택 데이터에 날짜 계산 정보로 전달하지 않는다. 현재 사이트에 수령 예정일 자동 계산은 연결되어 있지 않다.

## 구현 기준

1. 경매별로 한국 시간 기준 **방송 종료 시각**과 배송사별 **실제 출발 지점**을 저장한다. 공통 집하지를 쓰는 경매라면 판매업체 주소를 출발지로 추측하지 않는다. 일반 고객용 맡김일이나 맡김 마감일로 경매 수거 회차를 늦추지 않는다. 방송 종료일과 수거일이 같으면 실제 수거 시각·예약 가능 여부로 남은 회차인지 판단하고, 시간이 없으면 당일 발송을 임의로 확정하지 않는다.
2. 최신 일정 원본을 서버에서 모아 보관한다. 구매자가 페이지를 열 때마다 배송사 사이트를 호출하거나 새 브라우저를 띄우지 않는다.
3. 계산 결과에는 수거일(발송 예정일)·수령 예정일·근거 일정 버전·조회 시각·예외 상태를 함께 남긴다. 맡김일을 사용자 입력이나 필수 값으로 요구하지 않는다. 필요한 이동일과 수거·도착 지점의 운휴를 검증한다.
4. 구매자에게는 `수령 예정 9.23(수)` 정도만 표시하고, 자세한 출발 일정은 펼쳐서 볼 수 있게 한다. 일정 불일치나 휴무 차단은 `일정 확인 중`으로 표시한다.
5. 정상 건의 예정일은 자동 표시한다. 주관사의 일괄 확인을 필수 단계로 추가하지 않는다. 실제 예약 회차를 선택하거나 예약 결과를 반영하면 그 날짜를 우선한다. 화면을 다시 열었다고 예정일이 다음 주로 밀리면 안 된다.
6. 결제·수령정보 입력이 늦어 첫 회차를 놓치면 `다음 회차 확인` 대상으로 묶는다. 이미 확정한 다른 구매자의 회차까지 일괄 이동하지 않는다.
7. 직수령·업체 직배송·구매자가 직접 예약한 배송에는 두 배송사의 자동 날짜를 붙이지 않는다.
8. 배송일 변경과 비용 변경을 분리한다. 일정 조회가 낙찰 상태·결제 상태·배송비를 수정하거나 알림을 재발송하면 안 된다.

## 리소스를 제한한 자동 안내 설계

### 확인한 현재 구조

- `server.js`의 알림 작업은 서버에서 15초 주기로 기존 대기열을 처리한다. 노트북이나 밴드 브라우저를 켜둘 필요가 없다.
- 날짜 안내용 알림톡은 현재 저장소에 등록된 승인 템플릿 목록에서 찾지 못했다. 결제 확인·낙찰·수령정보 등록용 문구를 날짜 알림으로 바꾸어 보내지 않는다. 알리고에서 새 승인이 추가되었는지는 이번 조사에서 확인하지 않았다.
- 이번 조사 JSON을 공백 없이 직렬화했을 때 파르게 일정 7,085바이트, 도도시 일정·노선표 52,200바이트, 대구 출발 상세 옵션 6,683바이트로 합계 **65,968바이트**다. 이는 자료 크기 측정값이며 실행 중 전체 메모리 사용량이나 HTTP 수집 과정의 메모리 측정값은 아니다.

### 실행 방식

1. 처음 경매를 준비할 때 방송 종료 기준과 배송사별 출발 지점을 저장한다. 일반적인 방송 시간 변경은 운영자가 수정할 수 있어야 한다. 채널 이름의 숫자나 마지막 낙찰 시각을 방송 종료로 임의 해석하지 않는다.
2. 공용 일정은 서버에서 하루 한 번 갱신하고 모든 경매가 공유한다. 예약 회차 결정 시 자료가 오래되었으면 한 번만 추가 갱신한다. 동시에 여러 요청이 들어와도 같은 수집 작업을 공유한다.
3. 수집은 공개 HTTP 자료를 사용하며 상주 브라우저나 AI 호출을 사용하지 않는다. 한 번에 수집하는 요청 수와 본문 크기·시간 제한을 둔다. 실패하면 일정 간격을 늘려 재시도하고 직전 정상 자료를 보존한다.
4. 최초 배송지 등록, 배송사·지점 변경, 방송 기준 변경, 공용 일정 내용 변경 때만 해당 배송 묶음의 날짜를 다시 계산한다. 날짜 계산은 저장된 작은 자료로 수행하고 구매자 화면 조회가 외부 사이트 요청을 유발하지 않게 한다.
5. 구매자·업체·주관사 화면은 같은 계산 결과를 읽는다. 합배송 묶음은 한 번만 계산하며, 실제로 서로 다른 회차에 나뉜 개체들은 하나의 날짜로 억지로 합치지 않는다.
6. 입력 정보가 충분한 정상 건은 별도 승인 없이 예정일을 안내한다. 운휴·모순·마감 경과 건만 운영자 확인 대상으로 모은다. 과거 예정일을 보고 있다는 이유만으로 새로운 배송 회차로 자동 이동하지 않는다.
7. 알림톡까지 사용하기로 정하면 적합한 승인 템플릿을 연결한 후 기존 서버 대기열을 재사용한다. 수신자·배송 묶음·예정일 버전으로 중복을 막고, 날짜가 실제 변경된 경우만 변경 안내 후보를 만든다. 화면 조회만으로 알림을 생성하지 않는다.
8. 일정 데이터만으로 알 수 있는 것은 **예정**이다. 실제 수거·도착 완료는 배송사의 완료 정보나 운영자의 확인을 반영한다. 달력 날짜가 지났다는 이유로 발송 완료나 수령 완료를 자동 표시하지 않는다.

위 항목은 조사 당시 설계다. 이후 사용자가 **페이지 자동 표시만** 선택했고, 아래 구현으로 범위를 확정했다. 알림톡·문자 발송은 추가하지 않는다.

## 실제 구현 시 필요한 검증

- 두 배송사 모두 일반 고객용 맡김일을 건너뛰어도 방송 이후의 유효한 수거 회차를 선택하는지 검증
- 파르게 수거 이후 도착 회차, 개별 지점 예외, 제주 전환일, 출발보다 이른 도착 차단
- 도도시 1일/3일 이동, 지점 휴무, 9/24~9/27 휴가, 제주 2·4번째 요일, 같은 이름의 서로 다른 지점
- 자정·월말·연말·윤년과 한국 시간, 경매 당일 접수 마감
- 중복 요청·새로고침·재시작에도 확정 회차 보존
- 일정 수집 실패/원본 변경 시 이전 정상 자료 보존 및 근거 없는 날짜 표시 차단
- 공식 예약 결과와 대표 노선 교차 확인

이번 조사는 공개 자료의 조회·코드 분석이다. 예약 화면 종단 검증이나 실제 배송일 확정은 수행하지 않았다.

## 2026-09-18 구현 및 검증

- 경매별 `shippingDefaults.deliverySchedule`: 방송일, 두 배송사 출발 지점, 선택적 발송일 조정. 종료 시각 정보가 없으므로 방송 **다음 날부터** 수거 회차를 찾는다. 신규·기존 경매의 날짜를 이름에서 추측하지 않는다.
- 정상 일정은 구매자 수령지 아래, 업체 구매자 카드, 주관사 낙찰 내역 펼침에 `발송 예정 / 수령 예정`으로 표시한다. 직수령에는 표시하지 않는다.
- 순수 계산 함수로 페이지 요청 시 저장된 일정만 계산한다. 별도의 대량 계산 작업이나 고객별 외부 조회는 없다. 일정 조회는 비용·결제·경매·알림을 변경하지 않는다.
- 공용 자료는 DB에 보존하고 메모리에서 공유한다. 정상 자료는 24시간 재사용하며 분당 타이머는 갱신 시각만 검사한다. 신규 출발지는 하나의 비동기 수집 작업으로 추가한다. 동시 갱신은 합치고, 3일 이상 지난 자료로 날짜를 안내하지 않는다.
- HTTP만 사용한다. 요청 본문 최대 3MB, 개별 요청 15초, 파르게 전체 45초, 도도시 전체 90초 제한. 도도시 출발 지점 최대 8개 및 지점당 최대 24개 노선. 서버 종료 시 요청을 중단한다. 초과·원본 구조 변경·모호한 지점은 정상 자료를 덮어쓰지 않는다.
- 늦은 수령지 등록·변경은 `배송 일정 확인 중`으로 표시한다. 결제방식 수정으로 예정일이 변하지 않도록 수령지 등록 시각을 별도 보존한다. 기존 데이터는 종전 등록 시각을 최초 기준으로 사용한다.
- 발송일 조정은 경매·배송사 전체에 적용된다. 구매자별 다음 회차 배정이나 예약 완료·실제 도착 연동은 이번 범위에 포함하지 않았다. 달력만으로 실제 배송 상태를 완료 처리하지 않는다.
- 파르게의 공개 주간표 전체 순서가 바뀌면 수집을 중단한다. 도도시 동일 업체명의 지역 구분, 1일/3일 이동, 휴가 차단, 제주 회차를 확인했다.

검증: 릴리스 위험 등급. `npm run check` 및 신규 JS 6개 `node --check` 통과. `npm test` 통합 갱신 최종 **839/839 통과**. 데스크톱 `python -m unittest discover -p "test*.py"` **203/203 통과**. 중복·동시 갱신, 저장 실패, 재시작, 종료 취소, 날짜 경계, 다른 경매, 수령지 수정, 결제방식 수정, 기존 배송비·구매자 알림 불변, 출력 HTML 안전성 포함.

## 공용 배송정보 갱신과 통합

사용자의 추가 요청으로 파르게·도도시 거점·요금·일정을 **같은 수집·저장 작업**으로 통합했다. 공용 배송 페이지의 기존 최신정보 버튼도 같은 서비스를 사용한다. 랩팡은 이번 자동 갱신 범위에 포함하지 않고 기존 수동 버튼을 유지한다.

- 파르게 파트너 API와 예약 페이지의 요금표를 한 번 수집하며, 예약 페이지 번들을 순차적으로 읽고 요금표 발견 시 중단한다.
- 도도시는 과거 고정 상품번호 대신 현재 노선표에서 크레용 대구 출발 15개 노선을 읽는다. 같은 상품 옵션 응답에서 거점·금액·도착 요일을 함께 추출한다.
- 실제 공개자료 수집 결과: 파르게 요금 105개 거점 약 3.4초, 도도시 99개 거점 약 15.9초. 이는 이 실행의 관측값이며 응답속도 보장은 아니다.
- 배송사별 요금표·일정·갱신 버전을 한 트랜잭션으로 반영한다. 자료가 누락되거나 기존 거점의 25%를 초과해 갑자기 사라지면 기존 값을 유지한다. 기존 구매자에게 확정된 비용은 소급 변경하지 않는다.
- 최초 실패 → 1분 뒤 재시도 → 5분 뒤 두 번째 재시도. 계속 실패하면 운영자에게 문자 한 건을 기존 서버 발송 큐로 보낸다. 이후에는 1시간 간격 재시도하며 같은 장애에 추가 문자 없음. 재시작 후에도 중복 방지 상태를 보존한다.
- 두 배송사가 함께 실패해도 장애 기간에 문자 한 건이다. 모두 복구된 뒤 새 장애가 나면 다시 한 건 보낸다. 발송 전에 복구되었거나 설정이 꺼지면 남아 있는 알림을 폐기한다.
- 사용자가 수신번호 **01049278600**, **SMS**를 확인했다. 번호는 운영 설정에 저장하며 공개 구매자 응답에 노출하지 않는다. 갱신 실패용 알림톡을 임의 재사용하지 않는다. 문자: `[옹동2] 배송정보 갱신 실패. 공용 배송 확인 필요` (UTF-8 65바이트).
- 자동 갱신 상태·마지막 성공시각·알림번호는 공용 배송 페이지에서 확인/수정한다. 설정 API는 운영자 인증이 필요하다. 운영 서버의 SMS 준비 상태 및 실발송 모드도 읽기 전용으로 확인했다.
- 실제 메시지 전송 테스트는 하지 않았다. 가상 발송기로 실패·재시도·큐·복구·재시작·중복 방지를 검증했다. 서버 또는 발송 큐 저장소 자체가 완전히 중단되면 내부 작업만으로 즉시 장애 문자를 보낼 수는 없다.
