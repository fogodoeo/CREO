# 업체 사전 출품 흐름 제안

최신 상태: 업체 작성·피들 가져오기·사진·부모·하단 메뉴를 실제 API에 연결하고 임시 SQLite/비공개 로컬 파일로 검증했다. 운영 배포 전이다. 기존 18826 IndexedDB 디자인 예시는 유지하며 실제 API 예시는 18831에서 제공한다. 아래 검증 기록은 단계별 이력이다. 실제 고객 경매 변경, 원격 Supabase 업로드, 알림 발송은 하지 않았다.

실제 작성 화면은 `public/vendor-entries.html`, API 어댑터는 `public/vendor-entry-api.js`다. 실패한 사진·작성 복구본만 기기에 두고 공식 저장은 서버로 보낸다. 업체 미등록 첫 안내는 닫을 수 있으며 검토 요청 전에 등록한다. 낙찰 전 출품 / 낙찰 후 정산을 기본 화면으로 열고 세 하단 메뉴에서 같은 경매와 업체를 유지한다. 구매자는 최초 등록 이후 내 개체 / 배송·결제로 나눈다.

최종 검증은 서버 559개·PC 189개와 실제 API 브라우저 6개 시나리오 묶음이다. [최신 진행 기록](PRODUCT_EXPERIENCE_RENEWAL.md)과 [업체 화면 검증](ui-audit/VENDOR_ENTRY_CONNECTED.md)에 범위·실패 보완·남은 제한을 정리했다. 서버 피들 요청은 가상 응답으로 검사했고, 실제 원격 Supabase/Linux/Safari 및 장기 구매자 권한은 후속 작업이다.

## 진입점

업체 전용 링크를 경매 전에 전달한다. 같은 업체 페이지의 하단 고정 메뉴에 `출품 개체 / 낙찰·정산 / 업체 정보`를 둔다. 아이콘과 글자를 함께 표시하고 선택 메뉴를 파란색으로 구분한다. 상단에는 로고와 경매 선택을 둔다. 경매 전에는 출품 목록을 첫 화면으로 열고, 출품 접수 종료 후 기본 진입은 낙찰·정산으로 전환한다. 지난 출품은 출품 탭에서 계속 조회할 수 있다. 선택한 경매가 세 화면 이동 시에도 유지된다. 경매별 출품·낙찰·정산 내역을 분리하고, 끝난 경매도 결제 확인과 지난 내역 조회를 위해 남긴다. 기존 업체 계좌·연락처는 재사용하고 처음 온 업체만 한 번 등록한다.

미등록 업체가 출품 화면에 처음 들어오면 연락처·은행·계좌번호·예금주 등록 창을 한 번 연다. `나중에`, 닫기, 바깥 클릭, Escape로 닫을 수 있다. 다시 방문할 때마다 자동으로 열지 않는다. 미등록 상태에서만 출품 목록의 작은 등록 행과 업체 정보 메뉴의 점 표시를 유지한다. 등록 완료하면 두 표시를 없애고, 낙찰·정산 화면에도 설정 폼을 반복하지 않는다. 카드결제 사용 여부는 업체 정보에서 추가로 설정한다.

개체 초안은 업체 정보 등록 전에도 저장할 수 있다. 검토 요청 전에 필수 업체 정보를 확인하고 부족하면 입력 중인 개체를 유지한 채 등록 창을 연다. `저장하고 검토 요청`으로 완료하며, 등록 실패·취소 시 제출하지 않는다. 업체 정보만 버려도 뒤에 작성 중인 개체의 변경 상태는 유지한다. 저장하지 않은 변경은 화면이나 경매를 바꿀 때 저장·계속 작성·나가기를 선택한다. 등록된 계좌 변경의 기존 운영자 요청 정책은 유지한다.

개체 작성 화면에서는 하단 메뉴를 숨기고 `임시 저장 / 검토 요청`을 하단에 고정한다. 일반 화면에서는 하단 메뉴 공간과 모바일 안전 영역만큼 여백을 확보한다.

순서: 출품 목록 진입 → 업체 정보 확인·등록 및 개체 작성 → 검토 요청 → 운영자 확인·편성 → 경매 진행 → 낙찰·정산. 업체 정보를 등록하기 전에도 개체 초안은 작성할 수 있다.

## 개체 작성 화면

- 업체명·연락처·계좌는 페이지의 업체 정보에서 가져오며 개체마다 다시 묻지 않는다.
- 종은 해당 경매의 기본 종을 사용한다. 업체에게 개체명·업체 관리번호를 입력받지 않는다. 모프·성별(미구분 허용)·체중을 먼저 받으며, 저장 시 경매별 `출품 01` 같은 임시 구분 번호를 자동 부여한다. 최종 A01/B01은 운영자가 편성할 때 부여한다.
- 크기·체중, 시작가는 경매 운영 규칙에 맞게 받는다. 고정 시작가 경매는 미리 정해진 금액을 사용한다.
- 사진은 휴대폰 촬영·앨범 선택으로 추가한다. 사진 없는 등록도 가능하다.
- 부모 정보는 선택 항목으로 부·모 버튼을 둔다. 업체의 기존 부모 목록에서 고르거나 없으면 새로 등록한다. 사진·이름·관리번호·모프로 검색·구분하고, 최초 목록이 비었으면 신규 등록으로 바로 진입한다. 해칭일·크기·비고는 `추가 정보`에 둔다.
- 같은 부모는 여러 개체·여러 경매에서 재사용한다. 부모 관리에서 수정하면 연결된 모든 개체와 구매자 화면에 최신 이름·모프·사진을 보여준다. 이전 부모 버전은 변경 기록으로 보존하며 업체의 최신 수정 내용을 과거 제출 스냅샷으로 덮지 않는다.
- `임시 저장`과 `검토 요청`을 구분한다. 검토 요청 취소 후 수정·재제출할 수 있다. `복사해서 등록`은 후속 검토 대상으로 남겨두며 현재 미리보기에는 넣지 않았다.

## 피들 링크 가져오기

- 목록 상단에 `피들 링크로 가져오기`를 왼쪽 흰색 테두리 보조 버튼, `＋ 직접 추가`를 오른쪽 파란 주 버튼으로 나란히 둔다. 320px에서도 둘 다 한 줄이며 최소 56px 높이를 유지한다. 개체 작성 화면의 가져오기 바로가기도 유지한다.
- 업체가 공개 `/pet/{UUID}` 링크를 붙여넣으면 개체 사진(최대 3장), 모프, 성별, 크기, 체중, 해칭일·설명(있는 경우), 부·모 정보를 가져와 초안으로 저장한다. 업체가 확인 후 검토 요청한다.
- 판매 가격을 경매 금액으로 가져오지 않는다. 부모가 등록되지 않았으면 이름을 추측해서 만들지 않는다.
- 같은 업체·경매에서 같은 피들 개체를 재차 가져오면 기존 출품을 열고, 같은 부모 피들 ID는 기존 부모를 재사용한다. 재가져오기로 업체가 고친 부모 정보를 덮어쓰지 않는다.
- 로그인 세션이나 비공개 API를 쓰지 않고 공개 페이지의 JSON-LD/선언형 페이지 자료를 읽는다. 사이트 스크립트를 실행하지 않는다. 공식 제휴 API 연동은 아니므로 페이지 구조 변경·비공개 전환 시 재확인이 필요하다.
- 허용한 HTTPS 피들 개체 주소만 요청하고 외부 리다이렉트를 따르지 않는다. 사진은 해당 페이지에서 확인한 공개 이미지 주소만 가져온다. 타임아웃·응답 크기 제한을 적용한다.

## 운영자 검토

- `검토 대기 / 수정 요청 / 편성 완료`를 구분하고 필요한 건만 우선 보여준다.
- 제출된 개체·부·모 사진과 정보가 한 화면에서 확인되어야 한다.
- 수정이 필요하면 짧은 사유로 업체에 돌려보내고, 업체는 같은 초안을 수정해서 재제출한다.
- 운영자가 확정할 때 경매 번호·팀·순서를 배정한다. 업체가 A01/B01 등 송출용 번호를 직접 정하게 하지 않는다.
- 제출만으로는 진행 중 경매 목록이나 송출에 나타나지 않는다.
- 편성 후 업체가 수정한 내용은 변경안으로 받는다. 이미 편성된 개체·진행 중 입찰·확정된 낙찰 기록을 바로 덮어쓰지 않는다.

## 구현 경계

현재 운영 업체 페이지는 낙찰 후 결제 확인에 중심이 있다. 로컬에서 업체 전용 링크·공통 업체 프로필을 재사용하는 출품 API를 구현했다. 초안은 기존 경매 item과 별도 저장하며 운영자 편성에서 연결한다. 업체 작성 화면의 저장 어댑터를 실제 API로 전환하는 작업은 남아 있다.

같은 제출이나 운영자 반영 버튼의 재시도가 중복 개체를 만들지 않도록 하고, 업체는 자신의 출품만 수정할 수 있어야 한다. 운영자가 검토하는 도중 수정된 제출안은 다시 확인하도록 한다. 사진 업로드 실패는 개체 입력을 잃게 하지 않는다. 개체의 확정 정보와 부모 프로필의 최신 정보는 구분한다. 부모 정보는 업체가 수정한 최신 버전을 연결된 구매자 화면에서도 조회한다.

로컬 미리보기: PC 저장소 `scratch/checkout-redesign/entry-preview/`와 기존 `preview.cjs`에서 제공한다. 주소는 `http://127.0.0.1:18826/entry-preview/`이며 기존 역할 미리보기 메뉴에도 연결했다. 브라우저의 전용 IndexedDB에 가상 출품·부모·압축 사진을 저장하고, 운영자/구매자 역할은 화면 검토용이다. 로그인·업체 권한·실제 출품 배정의 운영 구현으로 간주하지 않는다. 브라우저/프로필이 달라지면 미리보기 자료도 분리된다.

업체 연락처·결제 설정은 미리보기 서버 메모리에만 저장하며 같은 예시 업체의 경매 간에 공유한다. 서버 재시작 시 초기화된다. 등록 창의 최초 표시 여부는 이 브라우저의 예시 업체별 localStorage에 보관하며 서버 공통 상태가 아니다. 미리보기 상단 `등록 완료 / 처음 등록 / 연결 오류`로 상태를 고른다. `예시 초기화`는 출품·부모 예시와 서버의 가상 거래 자료, 현재 예시 업체의 팝업 표시 기록을 초기화한다. 첫 진입 화면은 가상 경매의 출품 접수 상태로 분기하며, 운영 경매 단계·실제 업체 프로필 저장·서버의 제출 필수정보 검증은 배포 단계에서 별도 구현해야 한다.

- 운영 배포·실제 낙찰 반영·알림 발송·Supabase 업로드·실기기 Safari는 실시하지 않았다.

## 실제 API·운영자 화면 구현 — 후속

- 업체: `GET/POST /api/platform/vendor-entries`. 기존 전용 링크와 참가 경매 권한으로 자신의 자료만 읽고 쓴다. `save`, `submit`, `withdraw`, `revise`, `parent`를 지원한다. 클라이언트가 보낸 업체 ID·외부 사진 URL로 권한을 바꾸지 않는다.
- 운영자: `GET/PUT /channels/:id/entry-policy`, `GET /channels/:id/entries`, `POST /channels/:id/entries/review`. 기존 운영자 세션을 사용한다. 기존 경매의 접수는 기본 마감이며 자동으로 열지 않는다. 접수를 마감해도 이미 제출된 개체를 검토할 수 있다.
- `public/vendor-entry-review.html`에서 목록 → 개체 검토/편성 팝업 → 대기 item 반영까지 연결했다. 운영 페이지의 출품 검토 링크는 현재 경매를 유지한다. 업체명·상태·개체 요약을 목록에, 상세/사진/부모/편성 정보는 팝업에 둔다. 팀은 업체 설정을 기본으로 표시하며 해당 경매의 팀만 고를 수 있다.
- 응답 유실 후 재시도는 같은 requestId, 같은 내용으로 처리한다. 제출 버전이 달라졌으면 운영자가 최신 내용 다시 확인을 눌러야 한다. 입찰 시작·낙찰 item은 수정안으로 덮지 않는다. 새 제출 수정안과 승인된 옛 자료를 혼동하지 않는다.
- 부모 자료 수정은 최신 정보로 조회하되 이전 버전과 승인 스냅샷을 보존한다. 라이브 낙찰/결제 행은 수정하지 않는다. 실제 SQLite 재시작 후 구매자·업체 HTML에서 부모 정보 반영을 확인했다.
- 저장소는 공통 업체별 `vendor_entries_v1::<UUID>` 문서와 기존 `setting/entry-policy`를 사용한다. 미디어는 신뢰하는 서버 처리에서 등록한 메타데이터만 허용하며 파일 업로드 HTTP 경로는 아직 없다. 메타데이터 테스트가 실제 Storage 업로드 증거가 아니다.
- 검증: 출품 서비스 8개, 실제 API 집중 2개, 서버 전체 540개, PC 앱 189개 통과. 운영자 브라우저 검사는 `scratch/checkout-redesign/entry-review-check.cjs`, 구매자/업체 사진 연결은 `entry-integration-check.cjs`, 기존 화면 인접 회귀는 `buyer-navigation-check.cjs`에 있다.

이 절은 위 IndexedDB 미리보기와 구분한다. 미리보기의 피들 `import`, 사진 `media` 명령을 운영 API가 이미 지원한다고 간주하지 않는다. 파일 업로드·피들 가져오기·업체 작성 UI 연결과 다중 서버 저장 잠금은 후속 작업이다.

### 사진 HTTP 경로 후속 구현

`POST /api/platform/vendor-entries/photos`를 추가했다. 실제 업체 링크로 인증한 뒤 정지 사진을 서버에서 검증·압축해 비공개 파일로 등록한다. 실제 HTTP+임시 SQLite/파일로 구매자·업체 사진 조회와 재시작을 검증했다. 미리보기의 `Store.send({type:'media'})`가 이 경로로 자동 전환된 것은 아니다. 업체 작성 UI와 피들 가져오기는 다음 연결 작업이다. 서버 550개·PC 189개 테스트 통과, 원격 Supabase 실호출/운영 배포 없음. [사진 저장 구현 기록](ENTRY_PHOTO_STORAGE.md)에 계약과 제한을 정리했다.
