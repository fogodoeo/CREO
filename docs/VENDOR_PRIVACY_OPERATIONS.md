## 문의·탈퇴 요청

1. 요청 접수 시 연락처, 요청 범위와 접수일을 기록한다. 주민등록증 등 과도한 증빙을 기본으로 요구하지 않는다.
2. 로그인 계정과 해당 업체의 권한을 확인한다. 수정 가능한 업체 업무 번호만으로 계정 소유권을 판단하지 않는다.
3. 열람·정정·삭제·처리 정지·탈퇴 요청의 대상과 법정 보존 대상 여부를 확인한다. 법정 보존 대상은 관련 법률·항목·기간을 기록하고 접근을 제한한다.
4. 탈퇴 시 계정과 직원 소속을 정리하고 해당 계정의 세션을 폐기한다. 대표인 경우 진행 중인 예약·출품·정산과 다른 구성원에 미치는 영향을 먼저 확인한다.
5. 담당 개발자가 정확한 계정 식별값으로 운영 저장소, Supabase 미러, 관련 사진 및 알림 기록을 조회하여 삭제 계획을 만든다. 광범위한 문자열 검색/치환으로 다른 업체의 기록을 삭제하지 않는다.
6. 삭제 전 보존 사유와 범위를 검토하고 처리 결과를 안내한다. 기한 내 처리할 수 없으면 이유와 처리 일정을 안내한다.
7. 삭제 이력은 복원 시 재삭제에 필요한 최소한의 내부 식별값과 시각으로 관리한다. 연락처 원문을 삭제 이력에 중복 보관하지 않는다.
8. Render의 삭제 전 스냅샷은 최대 7일 남을 수 있다. 정상 서비스에서 이용하지 않으며, 복원 시 삭제 이력을 다시 적용한 뒤 서비스를 재개한다. Supabase 백업도 실제 보유 정책에 맞춰 동일하게 관리한다.

## 구현·검증

- `vendor-access.cleanupExpired`: 만료 후 1일이 지난 OTP·proof·session만 정리. 1회 100행 검사·최대 25행 삭제. 암호문을 검증하지 못한 행은 보존. 정리 중 새로 변경된 값은 건너뜀. 계정 디렉터리·업체·예약·거래 행은 대상에서 제외.
- 매분 실행하는 기존 인증 유지관리 작업에서 구매자·업체 정리를 각각 호출. 미러 삭제는 저장소의 기존 outbox를 통해 전달하므로 실패 시 재시도한다.
- 직원 참여 신청 전에 제공 대상·항목·목적·기간·거부 결과를 표시하고 필수 동의를 받는다. 서버도 동의 여부를 검사하며 버전과 시각을 요청에 보관한다.
- 로그인·가입·업체 정보 화면에 처리방침 및 문의 링크를 연결한다. 정산 계좌는 기능 이용 시 수집이며 최초 가입 필수 항목에 넣지 않는다.
- 위험도: 인증 임시 기록 정리와 서버 배포를 포함하므로 release. 서버 전체 863개, 데스크톱 203개 통과. 서버 테스트는 기존 tmp/CREO-live/node_modules 의존성을 NODE_PATH로 지정하여 실행했다.
