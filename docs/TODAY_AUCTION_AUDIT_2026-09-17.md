# 2026-09-17 크레용 방송 사전 점검

## 범위와 위험도

밴드 모니터링 앱 → 현재 채널/개체 → 낙찰 저장 → 구매자·업체 알림 → 수령·결제 → 주관사 배송비/인쇄를 점검했다. 이번 코드는 서버의 낙찰 저장/알림 등록 경계만 변경한다. `LIVE_RELIABILITY_CHECKLIST.md` 기준 **release/high** 위험이다.

실제 낙찰/결제/배송 기록으로 재현하지 않았다. 임시 SQLite와 가짜 발송 공급자를 사용했고 실제 톡·문자·프린터 발송은 하지 않았다. 노트북 앱을 종료하거나 재시작하지 않았다.

## 재현한 문제와 수정

| 문제 | 수정 | 검증 |
| --- | --- | --- |
| 낙찰을 저장한 뒤 알림 준비가 실패하면, 낙찰만 남거나 한쪽 알림만 등록됨 | 개체·송출 상태·구매자/업체 발송 대기를 SQLite 트랜잭션 하나로 저장 | 공급자 준비 실패와 실제 SQLite 트랜잭션 실패를 주입. 전체 롤백 후 재시작/재시도 성공 |
| 낙찰 취소·재진행 후에도 이전 낙찰의 대기 알림이 발송됨 | 발송 직전 개체의 낙찰 상태와 고유 낙찰 ID 확인. 이전 건은 만료 처리 | 취소 후 발송, 취소/재낙찰 후 발송 모두 이전 수신자에게 전송 없음 |
| 대기 중 이름/금액이 정정되면 이전 내용이 발송됨 | 발송 직전 현재 이름/금액·구매자 번호도 확인 | 이름/금액 정정 각각 이전 알림 만료 확인 |

알림 공급자 설정 장애는 낙찰 자체를 취소하지 않고 `configuration_pending`으로 보존한다. 재시작/설정 복구 후 양쪽 알림이 한 번씩 처리됨을 검증했다. 실제 전달 여부가 불명확한 기존 `delivery_unknown` 정책은 유지한다. 연락처 없는 구매자는 자동 발송 대상이 될 수 없으며 업체 알림은 따로 등록된다.

## 남은 확인 범위

- 오늘 실제 BAND 라이브 채팅의 수신/전송, 프리즘/OBS 송출, 프린터, 수신 휴대폰의 톡 도착은 모의 테스트로 대체할 수 없다. 실방 시작 전 짧은 운영 점검이 필요하다.
- 노트북 전원/인터넷이 끊기면 BAND 수집·채팅 전송은 중단된다. 서버에 이미 저장된 낙찰의 알림/구매자 웹 처리는 별개로 유지된다.
- 이미 공급자에게 접수된 톡은 낙찰 취소로 회수할 수 없다. 새 방어는 발송 전 대기 중인 이전 알림을 차단한다.
- 단일 Render 서버의 재배포 중 짧은 접속 중단 가능성은 남아 있다. 이번 배포는 진행 개체 0인 상태에서 수행한다.
