# 낙찰 → 연락 → 결제 → 확인 점검

## 범위와 판정

낙찰 전환 API, 서버 문자 대기열, 개인 결제 링크, 배송 저장, 입금 신고, 업체 확인을 코드 및 격리된 테스트 데이터로 점검했다. 결제 상태와 공개 응답 필드가 바뀌므로 release risk로 분류한다. 실제 경매 데이터에 낙찰·저장·결제 확인 테스트를 실행하거나 새 문자를 보내지 않았다.

## 수정 사항

1. **추가 낙찰 후 저장 버튼 잠김**: 과거 제출 시각만으로 저장 완료를 판단했다. 배송 기록이 없는 개체가 있으면 ‘추가 낙찰 내역 저장’을 제공하고, 저장 전의 계좌·카드 결제 실행을 막는다.
2. **입금 신고의 부분 변경**: 새 개체의 배송정보가 없는 경우 기존 개체를 신고 상태로 변경한 다음 409를 반환했다. 이제 전체 개체의 배송 기록을 먼저 검증한다. 반복된 실패 요청에도 기존 기록은 동일하게 유지된다.
3. **업체 확인 금액 불일치**: 입금 신고 이후 추가 낙찰이 생기면 화면은 신규 금액까지 합산했지만 서버는 신고된 묶음만 확정했다. 응답의 `confirmationDue`로 이번에 확정할 금액만 표시한다. 총 미결제액 `additionalDue`는 별도로 유지한다.
4. **확인 중 수정 시도**: 서버가 입금 신고 중 배송 변경을 거절하는데 화면에서는 수정·저장이 가능했다. 확인 중에는 관련 변경과 저장을 잠그고 상태를 표시한다.
5. **카드 링크 저장/문자 상태 구분**: 저장 성공과 문자 발송 대기·접수·실패·설정 대기를 구별해 안내한다.

## 검증

- API 회귀: 배송 저장/신고/확인 중복 요청, 추가 낙찰 전후 신고 금액, 재시작, 채널 격리, 카드 링크 흐름, 저장 누락 시 변경 없음.
- UI 회귀: 추가 낙찰 후 저장 활성화, 확인 중 잠금과 해제, 업체 확인 금액 표시, 문자 상태 안내.
- 기존 문자 회귀: 이벤트 중복 억제, 재시작 후 대기열, 설정 대기, 실패 재시도, 테스트 모드에서 실제 대기열 미소비.
- `npm run check`, 서버 전체 `npm test`, 데스크톱 `python -m unittest discover`, UTF-8 및 `git diff --check` 검사.
- 운영 문자 상태 조회 시점: SMS 설정 완료, testMode=false, 조회된 기록 sent=1 / failed=0 / queued=0. 이는 통신사 수신 완료 증명이 아니라 서비스의 발송 접수 기록이다.

## 운영상 남는 한계

- 전화번호가 없으면 낙찰자 문자를 보낼 수 없다. 실제 연락처 보완은 운영자가 해야 한다.
- 외부 문자 API 응답이 끊기는 경우 재시도와 실제 수신 사이의 정확히 한 번 전달은 보장하지 않는다. 문자 수신/입금 실물 검증은 이번 점검에서 수행하지 않았다.
- 서버 저장소 자체 장애로 알림 이벤트 등록이 실패하는 경우는 낙찰 성공과 분리되어 오류로 반환·기록된다. 기존에 등록된 문자 대기열의 재시도와는 다른 장애이며 운영 확인이 필요하다.
- 계좌 이체 및 카드 승인 확인은 업체의 수동 확인이다. 결제사 웹훅이나 은행 자동 대사로 전환한 것은 아니다.
