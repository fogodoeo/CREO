# 수령지·결제 방식 변경 승인

2026-09-08 / 위험도: Release (배송·결제 상태, 저장소, 공개 API 변경)

## 처리 흐름

1. 최초 수령지·결제 방식 저장은 즉시 적용한다. 계좌이체가 가능한 업체는 계좌이체를 기본 선택한다.
2. 이미 저장한 수령지 또는 업체별 결제 방식을 바꾸고 `변경 요청하기`를 누르면 요청만 저장한다. 기존 확정 정보·금액은 그대로 유지한다.
3. 운영자 `01049278600`에게 알림톡을 예약한다. 변경 요청과 알림 큐를 같은 저장소 트랜잭션에 저장한다.
4. 승인 대기 중에는 구매자의 결제 신고, 업체의 카드 링크 등록·결제 확인, 일반 배송 편집을 차단한다.
5. 운영자는 배송 관리의 `변경 요청` 또는 알림의 버튼으로 요청을 연다. 운영자 인증 후 변경 전후 수령지, 업체별 결제 방식, 배송비, 총액을 비교한다.
6. 미입금·카드 미승인을 확인하고 승인하면 전체 관련 배송정보와 요청 상태를 한 번에 저장한다. 기존 카드 링크는 제거하며 새 카드 결제는 업체가 새 링크를 등록한다.
7. 반려에는 사유가 필요하다. 기존 정보로 결제를 재개하고 구매자가 다시 요청할 수 있다.
8. 승인·반려 결과 확인용 구매자 알림을 보내고, 승인 시 관련 업체에 수령정보 등록 알림을 보낸다. 실제 결제 확인 완료 알림(UK_9278)은 이 과정에서 보내지 않는다.

## 알림 매핑

| 발생 시점 | 수신자 | 내부 키 / 승인 템플릿 | 링크 |
| --- | --- | --- | --- |
| 변경 요청 | 고정 운영자 번호 | operator_checkout_change / UL_0883 | /w/op_… → 운영자 인증 → 변경 승인 |
| 승인·반려 | 구매자 | buyer_checkout_change_reviewed / UL_0884 | 기존 /d/… 구매자 페이지 |
| 승인 | 관련 업체 | vendor_shipping_registered / UL_0883 | 기존 /w/… 업체 페이지 |

승인된 본문과 버튼 문구는 수정하지 않는다. 따라서 운영자 알림에도 기존 `수령정보 등록` 문구가 나오며, 구매자 결과 알림도 기존 `낙찰 내역 등록` 문구로 간다. 구체적인 변경 내용·승인 여부는 연결 페이지에 표시한다. 변경 요청·처리 결과 전용 문구가 필요하면 별도 템플릿 승인이 필요하다. 재사용 매핑 자체가 카카오의 용도 적합성 보장을 의미하지 않는다.

실패 시 문자 대체 설정은 기존 알리고 발송 실패 대체 기능을 사용한다. 설정 누락을 이유로 즉시 문자를 발송하지 않는다. 미등록 템플릿·발신 설정이나 통신사 문제까지 전달을 보장할 수는 없다.

## 보호 조건

- 구매자/채널마다 승인 대기 요청 1개. 동일 requestId 재전송은 같은 결과를 반환한다.
- 결제 신고·확인, 확인금액, 송장번호 또는 발송/수령 완료 상태가 있으면 신규 변경 요청을 차단한다.
- 요청 이후 개체·금액·배송정보·업체 설정이 달라졌다면 승인하지 않고 반려 후 새 요청을 받는다.
- 기존 외부 카드 링크는 사이트에서 삭제한다고 외부 결제서비스에서 취소되지 않는다. 운영자가 해당 서비스에서 취소·차단한 것을 확인해야 승인한다.
- 승인 대기 중에도 이미 복사한 계좌로 실제 이체하는 행위까지 막을 수 없다. 승인 직전에 관련 업체의 실제 거래 내역을 확인해야 한다.
- 운영자 링크에는 비밀번호나 구매자 전화번호를 넣지 않는다. 승인 API, 목록, 링크 조회 모두 운영자 인증을 요구한다.
- 다른 구매자/채널의 정보에 영향을 주지 않는다. 구매자 공개 응답에는 전화번호 원문, 요청 fingerprint, 운영자 코드를 내보내지 않는다.
- 채널 종료 후 승인할 수 없지만 반려하여 대기 요청을 정리할 수 있다.

검증: `test/checkout-change-requests.test.js`, 기존 배송/결제·알림·저장소 테스트, 서버 전체 검사, 데스크톱 전체 검사 및 로컬 브라우저 점검. 운영 데이터로 변경·결제 테스트하지 않는다.
