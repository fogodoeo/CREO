# 운영 화면과 경매 서버 분리

2026-09-12 준비본. 새 유료 서비스 생성과 운영 전환은 실행하지 않았다.

## 선택

현재 PC 앱은 안정화한 상태로 유지한다. 다음 운영 화면 개편은 웹으로 옮기되, PC에는 밴드 채팅 수집과 라벨 프린터 연결만 남기는 구성이 적합하다. 이번 작업에 전체 PC UI의 웹 이식은 포함되지 않는다.

| 구성 | 판단 |
| --- | --- |
| PC 프로그램에 모두 유지 | 현재 장비 연결을 유지하기 쉽지만 PC마다 배포가 필요하다. |
| HTML만 사용 | 별도 프로그램은 줄지만 밴드의 다른 탭 접근, 백그라운드 수집, 프린터 연결을 별도로 해결해야 한다. 현재 기능을 그대로 대체하지 못한다. |
| 웹 운영 화면 + 작은 PC 연결 프로그램 | 권장. 경매 상태는 서버 한 곳에서 관리하고 PC는 수집·출력 역할만 맡는다. |

## 이번에 준비한 배포 분리

```text
기존 구매자·업체 링크(creok.onrender.com/d, /s, /v, /w, /o)
  → 새 화면 서버의 같은 경로로 이동
새 화면 서버(gateway-server.js)
  ├ HTML, CSS, JS, 영상 제공
  └ /api 요청 → 기존 creok.onrender.com 서버
기존 서버
  └ 경매 처리 + SQLite 영구 디스크 + 알림 큐/발송
PC 밴드모니터
  └ 기존 서버에 계속 연결
```

기존 서버와 디스크를 이동하지 않으며, 경매 처리 서버와 발송 작업자를 복제하지 않는다. 기존 승인 알림톡의 링크 도메인도 유지한다. HTML/JS/CSS는 재검증 캐시를 사용한다.

화면만 수정하는 배포에서 기존 서버가 재시작되지 않는 효과가 있다. 기존 서버의 API/경매 처리 코드 배포에는 여전히 중단이 발생할 수 있다. Render는 영구 디스크가 붙은 서비스의 무중단 배포를 지원하지 않는다. 모든 배포의 무중단을 보장하는 구성은 아니다.

## 마지막 실행 단계

1. Render에서 같은 GitHub 저장소의 **새 Web Service** 생성. `deploy/render-gateway.yaml` 준비본을 사용하거나 아래 설정을 직접 입력한다. 기존 서비스를 새 Blueprint에 포함하지 않는다.
   - Build: `node --check gateway-server.js`
   - Start: `node gateway-server.js`
   - 환경변수: `CREO_BACKEND_URL=https://creok.onrender.com`, `CREO_PUBLIC_ORIGIN=https://creok.onrender.com`
   - Disk 없음. 기존 알리고/DB/밴드 비밀키를 복사하지 않는다.
   - 유료 최소 사양 `0.5c-512mb` 준비. 실제 월 요금과 지역은 생성 화면에서 확인한 뒤 확정한다. 이 작업에서 과금은 시작하지 않았다.
2. 새 주소에서 관리자 로그인, 구매자/업체/주관사 링크, P1~P3 송출과 동영상, 프린터 연결 화면을 확인한다. API 쓰기 검증은 별도 테스트 채널에서만 한다. 외부 OAuth를 사용한다면 등록된 리디렉션/허용 origin도 먼저 확인한다.
3. 기존 서비스의 자동 배포 필터에 `public/**`, `gateway-server.js`, `deploy/**`, `docs/**`를 Ignored Paths로 추가한다. 기존 다른 필터는 보존한다. 화면과 API를 함께 바꾸는 변경은 API 호환성을 확인하고 두 서비스를 순서대로 배포한다.
4. 기존 서비스에 `CREO_FRONTEND_ORIGIN=https://새화면서비스.onrender.com` 추가. 이 한 번은 기존 서버가 재시작될 수 있어 경매가 없는 시간에 전환한다.
5. 기존 단축 링크의 새 화면 연결과 `/health`, API, 로그인, 송출 갱신을 확인한다. 새 주소가 되었으므로 운영자 로그인·브라우저 로컬 설정은 한 번 다시 확인해야 한다. 서버에 저장된 개체·배송·결제 데이터는 그대로다.

사용자에게 필요한 최종 선택은 새 서비스의 유료 생성/요금 확정이다. 서비스가 생성된 뒤 위 전환 검증과 설정을 진행한다. **아직 위 1~5단계는 운영에 적용하지 않았다.**

## 복구

문제 발생 시 기존 서비스에서 `CREO_FRONTEND_ORIGIN`을 삭제하고 재배포한다. 기존 서버의 public 파일이 다시 표시되며 DB 복원은 필요하지 않다. 화면 전환 전후로 DB를 두 군데에서 쓰지 않으므로 데이터 합치기 과정도 없다. 새 화면 서비스는 필요하면 별도로 중지한다.

`tools/platform_snapshot.py`는 별도로 준비한 SQLite 백업/검증/빈 위치 복원 도구다. WAL을 포함하는 일관된 스냅샷, 해시·무결성 검증, 기존 대상 덮어쓰기 거부를 테스트했다. 이번 화면 분리에 DB 이전은 필요 없다. 백업에는 개인정보가 포함될 수 있으므로 Git/public에 두지 않는다.

## 검증과 한계

- 데스크톱: `python -m unittest discover -p "test*.py"` — 180개 통과.
- 서버: `npm run check`, `node --check gateway-server.js` 통과. `npm test` — 499개 통과.
- 서버 Python: `python -m unittest discover -s tests -p "test*.py"` — 85개 통과.
- 실제 core 프로세스 + 격리 SQLite + gateway: 단축 링크 리디렉션, 관리자 세션, 설정 쓰기, 화면 서버 재시작 중 core 생존, 재시작 뒤 데이터/인증 유지, 영상 Range, 전환 해제 후 기존 화면/데이터 복구 확인.
- gateway 장애/코어 장애 테스트는 API 실패를 명시적으로 반환하고 POST를 임의 재전송하지 않는지 확인했다. Render의 실제 트래픽 전환 시간/외부 OAuth/장시간 방송은 아직 검증하지 않았다.
- 알림 작업자 종료/재시작 테스트는 모의 발송 응답으로 확인했다. 알리고 응답 유실이나 발송 접수 후 DB 기록 실패는 `발송 결과 확인 필요`로 남기며 자동 중복 발송하지 않는다. 알리고 접수 성공은 실제 수신 단말 도착을 보증하지 않는다.
- PC 수신 로그는 재시작 시 미반영 메시지를 보존하지만 과거 입찰을 자동 재적용하지 않는다. 저장 실패가 계속되는 결과는 운영자 확인이 필요하다. 모든 경매 상태를 자동 복구하는 영구 전송 큐까지 구현한 것은 아니다.
