# 카드 안내·결제 신고와 알림 연결

2026-09-12. 위험도 **release**: 결제 상태, 영속 저장, 공개 결제 상태 계산과 API 응답을 수정했다. 로컬 코드·가상 자료만 사용했다. 운영 배포/재시작, 실제 고객 자료 변경, 실제 알림은 하지 않았다.

## 발견한 문제

- 카드 안내와 결제 신고가 개체별 `upsertRecord` 후 알림을 별도로 저장했다. 알림 준비 장애는 저장 성공 응답에 실패값만 붙었고, 중간 DB 실패는 앞의 개체만 변경했다. 이후 재시도는 중복 처리로 판단해 빠진 알림을 복구하지 못할 수 있었다.
- 마지막 요청 ID만 개체에 저장해서, 예전 성공 요청이 추가 낙찰 뒤 다시 들어오면 새로운 미결제 내역에 적용될 수 있었다. 이미 신고한 상태에 들어온 다른 요청 ID도 기억되지 않았다.
- 카드 안내를 다른 요청 ID로 다시 등록하면 기존 구매자의 결제 신고를 지우고 안내 대기로 되돌릴 수 있었다.
- 추가 낙찰의 수령정보 저장 시 이전 결제 개체와 새 개체의 저장 시각이 같아졌다. 상태 계산이 이전 결제 개체의 빈 카드 링크를 선택해서 새 카드 안내가 있어도 구매자는 준비 중으로 보거나 신고가 거절될 수 있었다. 완료 개체에 남은 카드 취소 표시도 추가 결제 확인을 막았다.
- 업체 알림의 결제금액이 이미 확인한 금액을 포함한 누적 금액이었다.

## 현재 처리

| 행동 | 함께 저장하는 내용 | 알림 |
| --- | --- | --- |
| 업체의 카드 링크 등록 | 미결제 개체의 안내 + 요청 영수증 + 알림 outbox | 기존 `buyer_card_link_ready` |
| 업체의 외부 앱 전송 확인 | 미결제 개체의 외부 안내 + 요청 영수증 | 추가 구매자 알림 없음 |
| 구매자의 결제 신고 | 신고 대상 개체 + 요청 영수증 + 알림 outbox | 기존 `vendor_payment_reported` |
| 같은 요청 재시도 | 원래 영수증으로 현재 상태 반환 | 새 알림 없음 |
| 이미 신고/결제된 상태의 다른 신고 요청 | 효과 없는 요청도 영수증 보존 | 새 알림 없음 |
| 공급자 설정 미완료 | 상태와 `configuration_pending` 알림 저장 | 기존 작업자가 설정 복구 후 처리 |
| 구매자 링크 중지 / 업체 전화번호 누락 | 입력한 업무 상태와 영수증 저장 | 발송 생략 사유 반환 |
| 알림 준비 또는 DB 배치 실패 | 업무 상태·영수증·알림 모두 미반영 | 재시도 가능 |

`checkout_action_v1::` 아래 경매·구매자 해시·업체·행동·요청 ID를 묶은 키를 사용한다. 카드 요청은 안내 방식/정규화 URL/확인 금액의 지문으로 내용이 다른 동일 ID를 거부한다. 영수증에는 사진/원문 전화번호/카드 URL을 저장하지 않는다. 새 시도 전 기존 요청을 확인하므로 이후 낙찰을 재처리하지 않는다.

모든 변경 shipment, 영수증, notification 행은 같은 `upsertRows` 배치다. 발송 공급자를 버튼 요청 안에서 호출하지 않는다. 링크 발급 메타데이터는 준비 중 별도로 갱신될 수 있지만, 실패한 업무의 결제 상태나 알림 예약이 일부 저장되지는 않는다. 기존 테스트의 enqueue-only 주입 어댑터는 호환 경로이며 원자적 outbox 보장은 실제 서버의 `prepare` 구현을 전제로 한다.

카드 등록 화면은 현재 `editVersion`을 보내고, 응답 유실 뒤 같은 폼을 다시 누르면 요청 ID를 재사용한다. 구매자의 신고도 같은 버전에서는 요청 ID를 유지한다. 새로고침 뒤에는 서버의 영수증과 등록 상태 검사가 중복 변경을 차단한다. 외부 전송 방식, 수령정보 선등록, 변경 승인 대기, 이전 카드 취소 확인, 보관 경매 제한은 유지한다.

추가 결제 상태는 미결제 shipment의 카드 정보를 우선 사용한다. 이미 결제한 개체의 오래된 취소 표시는 새 결제 확인을 막지 않는다. 구매자 카드 안내와 업체 신고 알림은 이번 미결제액을 표시한다. 5만 원 완료 뒤 4만 원 추가 낙찰 사례에서 이번 안내/신고액은 4만 원이다.

UI는 예약을 전달 완료라고 부르지 않는다. 정상 신고는 기존 ‘업체 확인 대기’ 화면으로 이어지고, 연락처/알림 설정 문제는 신고 저장과 구분해 안내한다. 카드 링크 저장 후 구매자 접속 링크가 중지되어 있다면 해당 사유와 운영자 문의를 표시한다.

## 증거

- `node --test test/checkout-notification-atomicity.test.js`: 실제 임시 SQLite **8개**. 준비 실패, DB 배치 롤백, 동시 요청, 같은 요청의 다른 본문, 재시작, 추가 낙찰 뒤 예전 요청/효과 없는 요청 재전송, 외부 전송, 공급자 설정 복구, 잘못된 링크, 보관 경매, 미등록 연락처를 검증했다. 가짜 공급자는 명시적 flush 전 호출되지 않는다.
- 수정 전 최초 2개 회귀 검사는 실패했다. 알림 준비 실패가 200으로 반환되고, 두 번째 shipment의 실패 뒤 첫 번째 개체가 변경되어 있는 것을 확인했다. 추가 낙찰 검사로 새 카드 링크가 있는데 ‘준비 중’으로 신고를 거절하는 오류도 확인했다. 수정 후 모두 통과했다.
- `test/checkout-core.test.js`: 같은 저장 시각에서 결제 완료/미결제 행 순서가 바뀌어도 새 카드 안내 선택. `test/checkout-actions.test.js`: 저장·예약·접수·설정/연락처 오류 문구 구분.
- PC 저장소 `node scratch/checkout-redesign/checkout-outbox-check.cjs`: 실제 업체/구매자 HTML + API + 임시 SQLite + Chrome. 서버는 처리한 뒤 HTTP 응답을 503으로 바꾸고 재시도했으며 요청 ID와 알림 한 건 유지, 링크 화면, 외부 앱 안내 무알림, 설정 오류 안내, 재시작 후 가짜 공급자의 한 번 처리 확인. 320/390/800px 가로 넘침 없음. 390px 카드/신고 화면을 직접 확인했다. 목록의 ‘처리 필요’ 필터가 처리 후 항목을 숨기는 정상 동작은 ‘전체’ 필터에서 검증했다.
- 인접 실제 화면: `buyer-navigation-check.cjs`, `payment-confirmation-check.cjs` 통과. 전자는 200% 확대 및 첫 등록/추가 낙찰/지난 경매 흐름을 포함한다.
- `npm run check`, 최종 `npm test`: **607/607**. PC `python -m unittest discover -p "test*.py"`: **189/189**. 수정 소스 strict UTF-8/U+FFFD 검사와 `git diff --check` 통과. 기존 PC 경고는 별도이며 이번 작업에서 제거하지 않았다.

## 남은 범위

실제 알리고 접수/전달, Render Linux와 실제 Supabase, 여러 서버 인스턴스의 동시 쓰기, 운영 배포 검증은 확인하지 않았다. 기존 프로세스 내 경매 잠금과 SQLite 배치가 이번 증거의 범위다. 이미 접수된 외부 메시지를 취소하거나 과거 운영 실패 알림을 소급 발송하지 않는다. 오래된 대기 알림의 업무 상태 변경 시점별 유효성 정책은 별도 검토가 필요하다.

전체 목표의 실제 인증 설정, 만료/계정 해제, 과거 기록 소유권 확인과 이관, 사진 Storage 실물 대조·보관/삭제 정책, 전체 역할/50개 HTML 흐름 감사는 계속 진행 대상이다. 이번 결제 연계 검사가 사이트 전체 완료를 뜻하지 않는다.
