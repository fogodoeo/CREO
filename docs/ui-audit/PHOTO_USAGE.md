# 출품 사진 저장량 — 로컬 구현과 검증

2026-09-12. 위험도 release: 저장소 조회 계약과 인증된 새 응답, 운영자 화면. 기존 쓰기/복구 API의 동작은 변경하지 않았다.

## 화면과 집계의 의미

운영자 **출품 검토 → 사진 저장량**에서 모든 경매의 출품 사진 등록량을 확인한다. 큰 숫자는 등록된 큰 사진+미리보기 크기의 합이다. 업체별 상세와 연결 용도는 필요한 경우에만 펼친다. 긴 내역을 스크롤해도 닫기/다시 조회는 유지한다.

- 같은 영속 사진 경로는 한 번만 합산한다. 사진의 큰 보기/미리보기 두 파일은 한 장의 등록 사진으로 묶는다.
- 출품 초안·제출·승인 자료, 현재 부모·이전 부모 버전, 구매자 보관함 스냅샷, 경매 원장에서 해당 사진을 참조하면 연결 중으로 센다. 용도별 수에는 중복이 있으므로 총 용량에 다시 더하지 않는다.
- `미연결`은 위 자료에서 연결을 찾지 못했다는 뜻이다. 삭제 가능 판정이 아니며 삭제 기능을 제공하지 않는다.
- 외부 사진과 예전 공개 사진/캡처 저장소는 등록된 비공개 출품 파일 용량에 넣지 않는다. 화면에 외부 사진 제외 수를 표시한다. 실제 Storage 청구량과 같은 숫자라고 주장하지 않는다.
- Storage 파일 목록·실제 크기는 아직 대조하지 않았다. 파일만 남은 업로드 실패 건/고아 파일, 다른 버킷 사용량과 트래픽은 포함하지 못한다. `objectVerification:false`, `deletionEnabled:false`를 반환한다.
- 암호화된 보관함을 읽지 못하거나 등록 정보가 없는 참조, 잘못된 영속 경로가 있으면 미연결 숫자는 `확인 필요`다. 읽지 못한 보관함의 용도별 수 역시 0으로 표시하지 않는다. 잘못된 미디어 크기/문서 파싱은 전체 오류로 표시한다.

## API와 조회 계약

`GET /api/platform/entry-photo-usage`는 운영자 인증이 필요하다. 업체/구매자 개인 링크로는 조회할 수 없다. 응답은 용량·장수·업체명·용도별 합계·불완전 사유이며 개별 사진 경로, 구매자 번호, 계좌를 내보내지 않는다. 저장·삭제 요청은 405로 거부한다. 응답 캐시는 `no-store, private`다.

`entry-photo-audit.js`는 등록 문서와 보존 참조를 두 번 읽어 지문을 비교한다. 중간에 자료가 바뀌면 불완전 집계로 표시하고 미연결 판단을 보류한다. 두 번 같은 자료를 확인했다는 뜻이며 DB 전체의 분산 트랜잭션 스냅샷이나 그 이후 변경 방지를 보장하지 않는다.

페이지당 250개, 두 번 조회 합계 최대 50,000행/64MB, 진행 시간 확인 30초로 제한한다. 페이지 사이에는 이벤트 루프를 양보한다. 동시에 열린 조회는 하나의 작업을 공유한다. 주기적인 자동 재조회·업로드/경매 잠금·DB 쓰기는 없다. Supabase의 한 요청 제한은 8초이며 전체 제한 시점에 이미 기다리는 요청은 해당 제한까지 이어질 수 있다.

새 `scanRowsByPrefix`는 정렬된 키 커서를 사용한다. Supabase 무결성 오류를 행 누락으로 숨기지 않고 실패한다. SQLite는 원격에만 있는 키와 로컬 변경을 합쳐 읽되 로컬 삭제 표시를 존중한다. 복구 읽기와 달리 캐시에 행을 쓰지 않으며 원격 조회 실패도 빈 목록으로 대체하지 않는다. 정렬·무결성·페이지 계약의 실제 Supabase 환경 검증은 미완료다.

## 검증

- `node --test test/entry-photo-audit.test.js`: 7개. 실제 임시 SQLite에서 공유 사진 중복 합산 방지, 과거 부모/보관함 보호, 불완전 참조와 암호화 키 오류, 조회 중 변경, 한도/파싱 오류, 원격·로컬·삭제 마커 커서 병합, 읽기 중 쓰기 없음, 가짜 Supabase 무결성/커서 계약, 운영자 인증과 조회 전용을 확인했다.
- SQLite 인접 검사 포함 18개 통과. 새 커서 테스트의 최초 실패는 SQLite 행 객체의 prototype 차이였고, 실제 키/값과 순서를 비교하도록 보완했다. 레코드 누락을 무시한 수정이 아니다.
- `scratch/checkout-redesign/photo-usage-check.cjs` (PC 저장소): 실제 HTML/API·가상 등록 문서로 합계와 펼침, 320/390/800px·긴 업체명·200% CSS 확대, 고정된 닫기/재조회, Escape/바깥 클릭/포커스 복귀, 조회 실패 시 옛 숫자 제거·재시도, 읽을 수 없는 보관함 상태와 쓰기 요청 없음 통과.
- 기존 `entry-review-check.cjs` 통과: 접수 시작/마감, 편성, 오래된 자료/중복 요청, 사진과 모바일 검토 흐름이 유지됐다.
- `npm run check`, 서버 전체 **597개**, PC 전체 **189개** 통과. 로그는 PC 저장소 `scratch/checkout-redesign/photo-usage-{check,server-tests,desktop-tests}.log`다. 기존 PC 경고는 남아 있다.
- `photo-usage-390.png`, `photo-usage-incomplete.png`를 직접 확인했다. 펼친 상세가 길어도 닫기·재조회가 보이도록 구조를 보완했다.

실제 Storage 파일 대조, 고아 파일 삭제/복구, 요금제 실제 사용량, 보관 기간 확정, Safari/스크린리더는 미검증이다. 이 단계는 보관 정책을 정할 기초 정보이며 자동 삭제나 정책 확정을 뜻하지 않는다. 운영 배포·재시작·고객 사진 조회/변경·실제 발송은 실행하지 않았다.
