# 입금 확인과 구매자 알림 연결

2026-09-12. 위험도 **release**: 결제 상태·영속 저장·API 응답 계약을 수정했다. 운영 배포/서버 재시작/실제 알림 발송은 하지 않았다.

## 재현한 문제

1. 운영 배송 화면에서 입금을 확인하면 결제 상태만 바뀌고 구매자 완료 알림이 없었다.
2. 업체 확인은 개체별 저장 후 알림을 별도로 저장했다. 중간 실패 시 일부 개체만 완료되거나 알림이 빠질 수 있었다.
3. 5만 원 결제 신고 후 4만 원 추가 낙찰이 생긴 상태에서 이전 5만 원을 확인하면, 완료 알림에 남은 4만 원을 넣었다.
4. 오래된 확인 요청을 새 낙찰 뒤 재전송했을 때 새 개체까지 확인될 수 있었다.
5. 실제 업체 화면에서 구매자가 결제 신고를 하지 않은 계좌이체/등록된 카드 링크에는 직접 확인 버튼이 없었다. API는 허용하지만 UI에서 도달할 수 없었다.
6. 운영자의 확인 질문이 조회한 최신 금액 대신 화면에 남은 금액을 사용했고, 수정 버전을 POST에 전달하지 않았다.

## 현재 동작

| 시작점 | 결과 | 구매자 알림 |
| --- | --- | --- |
| 운영자 입금 확인 | 해당 업체의 확인 대상 개체를 결제 완료 처리 | `buyer_payment_confirmed` 예약 |
| 업체 입금/결제 확인 | 같은 서버 처리 사용 | 같은 템플릿 예약 |
| 구매자 미신고·계좌이체 또는 등록된 카드 링크 | 진행 중 내역의 직접 확인 버튼 사용 가능 | 실제 확인 시에만 예약 |
| 구매자 링크 사용 중지 | 실제 결제 확인은 저장 | 발송하지 않고 링크 중지 표시 |
| 알림 공급자 설정 대기 | 결제와 `configuration_pending` 알림 함께 저장 | 기존 작업자에서 설정 복구 후 처리 |
| 알림 준비/저장소 실패 | 결제·확인 영수증·알림을 모두 미반영 | 재시도 가능 |
| 동일 확인 요청 재전송 | 현재 화면 상태 반환, 새 낙찰을 확인하지 않음 | 중복 생성 없음 |

모든 변경 개체, 확인 영수증, 알림 outbox를 한 `upsertRows` 배치로 저장한다. 영수증 키는 경매/구매자 전화번호 HMAC/업체/요청 ID의 HMAC이다. 금액·개체 ID·알림 ID·생성 시각을 저장하고 개인 링크로 노출하지 않는다. 알림 금액은 누적 확인액에서 기존 확인액을 뺀 **이번 확인액**이다. 앞서 신고한 개체만 확인했다면 나중 낙찰은 미결제로 유지한다.

운영자 POST도 경매 잠금 안에서 현재 경매·낙찰자·업체를 다시 조회한다. 프런트는 최신 조회의 `editVersion`을 보낸다. 보관 경매, 정보 변경, 카드 취소 필요, 승인 대기 등 기존 제한은 유지한다. 구매자 링크 발송 직전 세대 검사는 이전 단계와 동일하다.

UI는 결제 완료와 알림 전달 결과를 구분한다. 예약은 ‘발송 대기’, 공급자 접수는 ‘알림 접수’, 설정/링크 문제는 별도 안내다. 업체 확인 팝업에는 이름·이번 금액을 표시한다. 미신고 직접 확인은 회색 버튼으로 두고 ‘처리 필요’ 건수에 억지로 넣지 않는다. 모바일 피드백은 하단 메뉴 위에 표시하고 입력을 가리지 않도록 자동으로 사라진다.

- 기존 `test/vendor-checkout-flow.test.js`에 미신고 직접 확인과 차단 상태 회귀 1개, `test/checkout-actions.test.js`에 발송 상태 문구 회귀 1개 추가.
- PC 저장소 `node scratch/checkout-redesign/payment-confirmation-check.cjs`: 실제 운영자/업체 HTML+API+임시 SQLite+Chrome. 로그인·업체/구매자 선택·운영자 확인·버전/금액 전달·업체 미신고 직접 확인·구매자 상태 일치·320/390/800px 피드백·중지 링크 경고·DB 재시작 후 가짜 발송 한 번 확인. 실제 메시지는 없다.

## 남은 제한

- 실제 알리고 접수/전달, Render Linux·Supabase 운영 저장소, 여러 서버 인스턴스 동시 쓰기는 이번 로컬 검사로 입증되지 않는다. 공급자 미설정/재시도/72시간 알림 만료 정책은 기존 작업자 정책이다.
- 서버는 `CheckoutNotificationService.prepare`를 사용한다. 과거 테스트의 enqueue-only 주입 어댑터에는 호환 경로가 남아 있으며 원자적 outbox 보장은 실제 prepare 구현을 전제로 한다.
- 이미 완료된 운영 결제를 역으로 찾아 알림을 보내지 않는다. 이번 적용 이후의 새 확인에 대한 수정이며 운영 자료 backtest/이관은 하지 않았다.
- 링크가 중지되어 건너뛴 알림은 링크 복구만으로 소급 발송하지 않는다. 실제 입금 확인과 고객 연락은 서로 다른 상태다.
- 카드 링크 등록·구매자 결제 신고의 원자적 outbox는 [후속 감사](CHECKOUT_NOTIFICATION_ATOMICITY.md)에서 수정/로컬 검증했다. 계정 보관함도 후속 구현되었지만 실제 인증 설정/과거 거래 이관과 전체 50개 HTML의 실제 흐름 검증은 계속 남아 있다.
