# CREO 운영 데이터 경계

이 문서는 설문을 제외한 경매·방송·배송·캡처 화면이 같은 데이터를 다르게 해석하지 않도록 지켜야 할 계약을 기록한다.

## 채널과 저장소

- `cdcup`의 경매 개체는 기존 Supabase `items`가 원본이다.
- 그 외 채널의 개체·업체·배송·방송 상태는 `creo_v2::<channel>::...` 레코드가 원본이다.
- 활성 채널 API 확인에 실패하면 데스크톱 앱은 마지막으로 검증된 채널을 유지하고 빈 목록을 표시한다. 다른 채널이나 CDCUP로 자동 전환하지 않는다.
- 서버용 Supabase 주소·키와 `CREO_ADMIN_SECRET`은 배포 환경변수로만 주입한다. 소스 기본 프로젝트나 관리자 비밀번호를 두지 않는다.

## 경매 상태

브라우저와 서버는 `public/auction-contract.js`, 데스크톱 앱은 `auction_contract.py`를 사용한다.

| 정규 상태 | 호환 입력 예시 | 의미 |
|---|---|---|
| `waiting` | `대기` | 시작 전 |
| `live` | `진행`, `진행중`, `경매중`, `active` | 진행 중 |
| `sold` | `낙찰`, `낙찰-대기`, `낙찰-입금완료`, `완료` | 낙찰 완료 |
| `passed` | `유찰`, `unsold` | 유찰 완료 |
| `cancelled` | `취소`, `canceled` | 취소 완료 |

집계·대진·방송·배송 화면에서 상태 문자열을 직접 비교하지 않는다.

## 운영 페이지 소유권

운영자는 메인에서 아래 순서만 사용한다. 같은 값을 두 화면에서 수정하지 않는다.

1. **경매 관리** (`channel-workspace.html`): 업체·결제정보, 개체·순서의 원본
2. **방송 진행** (`broadcast-studio.html`): 활성 채널, 현재 개체, 1P·2P 공용 화면과 3P 모듈
3. **배송·결제** (`shipping.html`): 구매자 안내 링크, 배송지, 업체별 결제 상태의 원본
4. **정산·인쇄** (`print.html`): 확정 자료 조회, 구글시트, 라벨 출력

- 경매 관리의 배송 탭은 요약만 보여 주고 수정은 배송·결제 페이지로 보낸다.
- 경매 관리·방송 설정·배송·인쇄 같은 운영 페이지는 URL에 명시된 `channel`만 사용한다. 채널이 없거나 존재하지 않으면 현재 활성 채널로 추측하지 않고 중단한다.
- 배송·전체조회·인쇄는 `operation-channel.js`에서 같은 채널 검증과 데이터 어댑터를 사용한다. 서버가 다른 채널을 반환하면 표시하거나 저장하지 않고 중단한다.
- 운영 페이지 사이의 링크는 `channel-runtime.js`의 공용 경로표로 만든다. 채널 설정에 남은 과거 링크가 다른 채널로 이동시키면 안 된다.
- `channel-shipping.html`은 과거 주소 호환용 리다이렉트이며 별도 상태나 편집 코드를 갖지 않는다.
- 구매자 페이지는 `/s/{접속코드}`, 업체 페이지는 `/v/{업체접속코드}`만 사용한다. 전화번호나 업체 ID를 공개 URL에 넣지 않는다.
- 구매자·업체 페이지는 별도 운영 데이터 사본을 만들지 않고 같은 shipment/checkout 상태를 역할별로 제한해 표시한다.
- 구매자 링크에는 해당 업체의 등록 연락처만 문의 수단으로 표시한다. 이 연락처는 접속코드로 보호된 결제 응답에만 포함하고 공개 방송 응답에는 포함하지 않는다.
- 회차·캡처·핀볼·배송 요금표는 보조 도구이며 핵심 파이프라인과 별도 원본을 만들지 않는다.
- 네 핵심 운영 화면은 `operator-pipeline.js`의 같은 단계 표시줄을 사용한다. 현재 채널 ID를 모든 링크에 보존하며, 경매 관리 화면 안에 방송·배송·인쇄 링크를 다시 복제하지 않는다.
- 구매자와 업체의 접속코드 페이지에는 운영자 단계 표시줄이나 채널 설정 링크를 노출하지 않는다.

## P1·P2 공용 송출 규칙

- 데이터 어댑터와 채널 프로필에 관계없이 P1·P2 송출은 모두 `auction-live.html`, 배치는 모두 `platform-layout-editor.html`을 사용한다. 레거시 호환 엔진은 채널 고유 연출이 필요한 P3에만 허용한다.
- 채널 생성·복제 시 HTML이나 CSS 사본을 만들지 않는다. 채널에는 문구, 표시 여부, 위치, 크기, 폰트 배율, 투명도 같은 설정값만 저장한다.
- 채널 복제는 공용 화면의 배치·표시 규칙만 이어받는다. 진행자명, 자막, 배너 주소와 이전 방송 진행 상태는 새 채널로 복사하지 않는다.
- 따라서 P1·P2 렌더러의 버그 수정은 기존 플랫폼 채널과 이후 생성되는 채널에 동시에 적용된다.
- 방송 프로필은 P3의 집계·대진·주사위 같은 정체성 모듈만 고른다. 프로필이 P1·P2 파일을 교체하게 만들지 않는다.
- `cdcup`의 `legacy-cdcup` 어댑터는 P3 대진 연출만 검증된 기존 송출을 유지하는 호환 경계다. P1·P2는 동일한 공용 엔진을 쓰며, 이 P3 예외도 신규 채널에는 복제하지 않는다.

## CDCUP 라운드

- 3라운드 진출 명단은 2라운드 종료 트랜잭션에서 확정하고 고유 `tournament_run_id_4`와 함께 저장한다.
- 목록 순서는 `A01~H01`, `A02~H02`, `A03~H03`이다.
- 진행 중인 3라운드는 저장된 명단 스냅샷만 신뢰한다. 2라운드 금액이나 과거 아카이브에서 다시 계산하지 않는다.
- 회차 ID가 없는 과거 명단만으로 빈 목록이나 일부 목록을 복구하지 않는다.

## 변경 검증

1. `npm run check`
2. `npm test`
3. `scripts/verify-platform-integration.js`로 채널별 개체·업체·배송·방송 상태 격리 확인
4. CDCUP 목록, 방송 1~3P, 배송, 전체 대진을 데스크톱·모바일 폭에서 확인

새 이벤트 기능은 채널 설정이나 별도 모듈로 추가한다. 실제 업체명, 특정 회차 결과, 관리자 비밀번호를 공용 화면의 기본값으로 추가하지 않는다.
